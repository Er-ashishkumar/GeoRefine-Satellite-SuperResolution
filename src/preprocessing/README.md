# src/preprocessing — Phase 2: Preprocessing & Alignment

Consumes `data/processed/dataset_index.json` (Phase 1, `src/dataset/`).
Produces `data/processed/preprocessing_index.json` and, for scenes without a
real HR reference, a synthetic LR raster under
`data/processed/synthetic_lr/<scene_id>/synthetic_lr.tif`.

Phase 1's `src/dataset/` and `dataset_index.json` are not modified by this
phase. Phase 2 reads that index and writes its own output so both phases'
contracts stay independently stable — see the module docstring in
`pipeline.py` for the full reasoning.

## What each module does

- **`bands.py`** — identifies Sentinel-2 band tokens in filenames
  (`B04`→`B4`, `B8A` stays `B8A`, ...) and stacks a scene's matched
  single-band LR files into one `(bands, H, W)` array. Verifies the matched
  files share the same CRS, size and resolution before stacking — a
  mismatch is reported as an issue, never silently resampled at this stage.
  A single pre-merged multi-band composite file is passed through, but its
  band order is flagged as unverified (Phase 2 cannot infer band order from
  pixel data alone).
- **`alignment.py`** — for scenes **with** a real HR reference: checks CRS
  match, LR:HR resolution ratio vs. the expected scale factor, and spatial
  bounds overlap (reprojecting bounds with `pyproj` when CRS differs).
  `reproject_hr_to_lr_grid()` does the actual pixel-level reprojection
  (`rasterio.warp`) once a pair is confirmed worth aligning.
- **`synthetic_hr.py`** — for scenes **without** a real HR reference (and
  `dataset.synthetic_hr_fallback.enabled: true` in `config.yaml`): generates
  the synthetic-fallback training pair. See the concrete interpretation
  documented at the top of that file — briefly, the real LR imagery is used
  as an unverified "proxy HR", and a synthetic LR companion is generated by
  Gaussian-blurring and block-mean-downsampling it. No HR-side pixels are
  invented; only the LR side is synthetically degraded from real data.
- **`pipeline.py`** — orchestrates the above per scene and writes
  `preprocessing_index.json`.

## `preprocessing_index.json` schema

```json
{
  "num_scenes": 2,
  "num_scenes_with_real_hr_aligned": 1,
  "num_scenes_synthetic_hr": 1,
  "num_scenes_with_issues": 0,
  "scenes": [
    {
      "scene_id": "string",
      "phase1_issues": ["carried forward from dataset_index.json, if any"],
      "is_synthetic_hr": true,
      "band_stack": {
        "ok": true,
        "band_order": ["red", "nir"],
        "source_files": ["data/raw/.../B04.tif", "..."],
        "issues": []
      },
      "alignment": [
        {
          "hr_file": "data/raw/.../ref.tif",
          "crs_match": true,
          "resolution_ratio": 4.0,
          "expected_ratio": 4,
          "bounds_overlap_fraction": 1.0,
          "is_aligned": true,
          "issues": []
        }
      ],
      "synthetic": {
        "proxy_hr_paths": ["data/raw/.../B04.tif", "..."],
        "synthetic_lr_path": "data/processed/synthetic_lr/<scene_id>/synthetic_lr.tif",
        "band_order": ["red", "nir"],
        "blur_sigma": 1.0,
        "downsample_factor": 4,
        "proxy_hr_shape": [2, 64, 64],
        "synthetic_lr_shape": [2, 16, 16]
      },
      "issues": []
    }
  ]
}
```

`alignment` is `[]` and `synthetic` is `null` for a scene using the other
path (they're mutually exclusive per scene — a scene either has a real HR
reference or uses the synthetic fallback, never both). `band_stack` is
`null` only when a scene had no LR files at all.

## Config (`config.yaml`, additive — Phase 1's `dataset:` section is unchanged)

```yaml
preprocessing:
  output_index_filename: "preprocessing_index.json"
  synthetic_output_subdir: "synthetic_lr"
  min_overlap_fraction: 0.5
  resolution_ratio_tolerance: 0.15
```

## CLI

```
python scripts/run_preprocessing.py
```

Requires `data/processed/dataset_index.json` to already exist (run
`scripts/build_dataset_index.py` first). Exits with an error and a clear
message if it doesn't.

## Known limitations (for Phase 3+)

- `bands.py` only resolves the two bands named in `config.yaml`'s
  `sentinel2` section (red, nir). Extending to more bands means adding more
  entries to the `requested_bands` dict passed to `load_band_stack` — no
  structural change needed.
- Pre-merged multi-band composite LR files are read but their band order is
  never verified against `red_band`/`nir_band` — only single-band files get
  that guarantee. If real scenes arrive as composites, this needs a
  band-order convention documented in `data/README.md`.
- `check_alignment()` works at the metadata/bounds level; it does not
  measure sub-pixel registration accuracy (cross-correlation etc.). That
  belongs to Phase 6 (Validation & Metrics) once real paired imagery
  exists, per `data/README.md`'s target of "sub-pixel (< 1 LR pixel)
  co-registration offset where possible".
- Everything here has only been exercised against synthetic test GeoTIFFs
  (no real Sentinel-2 imagery has been added to `data/raw/` yet, per the
  Phase 1 handoff). Band-name matching in particular should be re-checked
  once real Sentinel-2 filenames are in play — they may include additional
  tokens (tile ID, date, resolution suffix) that `canonical_band_name()`
  should already tolerate, but this is worth confirming.
