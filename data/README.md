# Data directory

This folder is not committed to git (see `.gitignore`) except for the
`.gitkeep` placeholders that keep the folder structure intact in a fresh
clone.

## Expected raw data layout

    data/raw/<scene_id>/lr/*.tif   (required - medium-resolution Sentinel-2 imagery)
    data/raw/<scene_id>/hr/*.tif   (optional - real high-resolution reference imagery)

- `<scene_id>` is any folder name you choose to identify one acquisition
  (e.g. `2024-06-12_tileA`, `sentinel2_20240612_T43QCV`).
- `lr/` must exist for a scene to be picked up by the dataset indexer. It
  may contain a single multi-band composite file or several single-band
  files (e.g. separate `B04.tif`, `B08.tif`) - Phase 1 only records
  metadata per file; merging/aligning bands happens in Phase 2
  (preprocessing).
- `hr/` is optional. If present, it should contain genuinely independent
  high-resolution reference imagery for that scene (e.g. a PlanetScope or
  aerial image covering the same area), used for supervised training
  and validation.

## Dataset strategy

**Preferred:** Sentinel-2 medium-resolution imagery paired with real,
independently-sourced high-resolution reference imagery (e.g. PlanetScope,
aerial photography, or Google Earth exports), co-registered with QGIS or
equivalent tools.

**Fallback (when no real HR reference is available):** a synthetic HR
proxy is generated by taking a high-quality image and applying Gaussian
blur + downsampling (see `dataset.synthetic_hr_fallback` in `config.yaml`)
to simulate what a lower-resolution sensor would have captured. This is a
**synthetic degradation**, not real ground truth, and is documented as
such everywhere it is used - model outputs trained or validated against a
synthetic HR proxy describe how well the model reconstructs a known
degradation, not how well it recovers real-world detail that was never
captured.

Any scene using the synthetic fallback must be flagged as such in the
dataset index (`is_synthetic_hr: true`), which will be added in Phase 2
once the fallback degradation pipeline exists.

## Target dataset size (Phase 3 - LR/HR patch generation)

- 200-500 matched patch pairs
- 128x128 or 256x256 patches
- sub-pixel (< 1 LR pixel) co-registration offset where possible
- manual visual inspection of a representative sample of pairs

## Dataset index

Run `python scripts/build_dataset_index.py` from the repo root to scan
`data/raw/` and produce `data/processed/dataset_index.json`. This index
lists, per scene: every LR/HR file found, its CRS, resolution, size, band
count, and any metadata-level issues (missing CRS, zero-size raster, etc.).
It does not load pixel data, so it is safe and fast to re-run at any time.

Later phases (preprocessing, patch generation) read this index instead of
re-scanning the filesystem, so **do not hand-edit it** - re-run the script
after adding or changing raw data.
